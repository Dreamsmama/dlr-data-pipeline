# 内部数据 · 飞书历史记录浏览设计

## 1. 目标与使用场景

在数据采集后台新增“内部数据”入口，并把飞书会话拆分为“飞书群组”和“飞书单聊”两个一级模块，各自展示对应会话。内部管理员可以选择会话、按飞书消息发送时间筛选、查看采集后的正文和附件。会话分类字段、兼容策略和扩展验收标准见 `docs/feishu-chat-category-design.md`。

当前使用场景是单租户、内部管理员、低并发浏览；采集任务可能同时写入新消息。PostgreSQL 是内部数据的权威查询源，私有 OSS 是附件的权威存储，本地任务目录仅用于暂存、断点恢复和历史回填。

本功能不引入新的登录系统。生产部署必须在现有内网、反向代理或统一身份认证后开放；在没有访问控制的公网环境中不得暴露内部数据 API。

## 2. 已确认的产品口径

- 不选择日期时查询所选群组的全部历史数据。
- 日期依据是飞书消息发送时间 `create_time`，界面按北京时间（UTC+8）解释。
- 日期选择精确到小时；开始小时包含，结束小时包含整个小时。API 内部使用“开始时间包含、结束时间排除”的半开区间，避免毫秒边界遗漏。
- 每页固定 20 条。
- 第 1 页永远是当前筛选结果中最新的 20 条，第 2 页是再往前的 20 条。
- 默认在当前页内按“旧内容在上、新内容在下”展示；切换后按“新内容在上、旧内容在下”展示。切换展示顺序不会把第一页改成最早的 20 条。
- 消息卡片复用采集页时间线组件，保持发送人、发送时间、消息类型、回复关系、正文、删除状态、附件和消息 ID 的展示一致。

## 3. 页面信息架构

路由：`/internal-data`

```text
内部数据
├─ 数据分类
│  ├─ 飞书群组
│  └─ 飞书单聊
├─ 会话列表
│  ├─ 群组或单聊 A（消息数、最近消息时间）
│  └─ 群组或单聊 B（消息数、最近消息时间）
└─ 群组数据区
   ├─ 群组名称与统计
   ├─ 开始小时 / 结束小时 / 应用 / 清空
   ├─ 正序或倒序切换
   ├─ 消息时间线（每页 20 条）
   └─ 首页 / 上一页 / 页码 / 下一页 / 末页
```

默认选择最近有消息的群组。筛选、群组和页码变化时显示加载状态；无群组、无匹配数据、配置缺失和接口失败分别显示可读提示。筛选条件和群组写入 URL 查询参数，刷新后可恢复当前视图。

## 4. 查询与分页设计

### 4.1 API

- `GET /api/internal/feishu/chats`
  - 返回群组 ID、名称、描述、去重消息数、最早/最近消息时间和最近采集时间。
- `GET /api/internal/feishu/chats/:chatId/messages`
  - 参数：`page`、`pageSize`、`order`、`from`、`to`、`snapshot`。
  - `pageSize` 默认并限制为 20（API 保留上限保护）。
  - `from` 包含，`to` 排除；前端把用户选择的结束小时转换为下一小时。
  - 首次请求生成 `snapshot`，后续翻页复用，避免采集期间新增消息导致总数和页码持续漂移。
  - 按 `create_time DESC, message_id DESC` 选择“最新窗口”，再依据 `order` 决定当前页内正序或倒序。
- `GET /api/internal/feishu/messages/:messageId/attachments/:fileKey`
  - 校验附件确实属于该消息。
  - 已上传 OSS 时返回短时签名地址；否则在本地暂存仍存在时走受限文件读取；不暴露 AccessKey、Bucket 长期公开地址或任意文件路径。

### 4.2 数据正确性

- `feishu_messages.message_id` 继续作为幂等主键，同一消息重复采集只更新，不重复展示。
- 所有查询必须带 `chat_id`，防止群组串数据。
- 同一发送时间使用 `message_id` 作为稳定次排序键。
- 无发送时间的历史异常数据在不筛选日期时保留并放在旧数据末端；启用日期筛选时自然排除。
- 使用现有 `(chat_id, create_time, message_id)` 索引；新增适合“最近消息优先”的索引，保证大量历史数据下第一页和时间范围查询不退化为全表排序。

## 5. 历史数据回填

现状：本地存在 5 个任务、69 条任务内记录，包含重复采集；PostgreSQL 当前只有 1 条消息，并存在明显的 `oc_demo` 测试群。

提供独立回填命令，行为如下：

1. 默认只做 dry-run，列出任务、群组、页数和消息数，不写数据库或 OSS。
2. 只有显式传入 `--apply` 才执行。
3. 支持 `--exclude-chat=<chatId>`，正式回填时排除 `oc_demo`，避免测试数据污染内部数据。
4. 按现有确定性 OSS Object Key 上传附件，按数据库主键幂等 upsert；重复运行不增加消息或附件记录数。
5. 单页失败时停止并报告任务/页号，不伪装完成，不删除本地任务文件。

## 6. 代码结构

- `packages/database`：增加飞书群组汇总、消息分页、附件定位查询。
- `packages/storage`：增加私有对象短时签名下载地址。
- `apps/api`：增加内部数据 API、参数校验、错误映射和历史回填命令。
- `apps/web/app/components`：抽取采集页和内部数据页共用的飞书时间线组件。
- `apps/web/app/internal-data`：实现分类、群组、时间筛选、排序和分页。
- 首页“内部资料”卡片改为可进入的“内部数据”入口；采集入口继续保留。

## 7. 验收标准

1. 从首页可以进入“内部数据”，看到“飞书”分类和数据库中的群组分类。
2. 默认选中最近活跃群；不选择日期时统计全部去重消息，第一页恰好展示最新 20 条（不足 20 条时全部展示）。
3. 默认当前页顶部较旧、底部较新；切换倒序后顶部最新，并且消息集合不变。
4. 每页固定 20 条；静态数据集跨页不重复、不遗漏，第一页/上一页/下一页/末页边界正确。
5. 选择北京时间 `10:00` 至 `12:00` 时，包含 `10:00:00` 到 `12:59:59.999...`，不包含 `13:00:00`；开始晚于结束时前端和 API 都拒绝。
6. 切换群组后不会展示上一群组的请求结果；URL 刷新后恢复群组、筛选、排序和页码。
7. 正文、富文本去重、删除态、回复关系、图片预览、附件下载与采集页布局一致。
8. 私有 OSS 附件只通过短时签名地址访问；非法消息/附件组合和路径穿越返回 404。
9. PostgreSQL 未配置时接口返回明确的 503 配置提示，页面不会假装“没有数据”。
10. 历史回填 dry-run 不写数据；`--apply` 重复执行后消息/附件数量不增加；正式运行排除 `oc_demo`。
11. `corepack.cmd pnpm test`、`typecheck`、`build` 全部通过。
12. 启动 Web/API 后，按“首页 → 内部数据 → 飞书 → 选择群组 → 默认最新 20 条 → 选择小时范围 → 切换排序 → 翻页 → 打开附件”的用户流程实测；失败步骤单独列出。

## 8. 暂不纳入本轮

- 关键词全文搜索、发送人筛选、跨群搜索和导出。
- 多租户数据隔离、细粒度群组权限和审计日志。
- 群组自定义标签、收藏、批量删除或内容编辑。
- WebSocket 实时推送；当前用筛选/翻页快照保证浏览稳定，重新进入或刷新可看到新采集数据。
