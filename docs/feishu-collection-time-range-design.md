# 飞书历史采集时间范围设计

## 1. 目标与使用场景

内部管理员在“飞书历史采集”页面选择一个群聊，并指定北京时间的开始、结束分钟。系统只向飞书抓取该时间段内按消息发送时间 `create_time` 命中的消息，避免全量扫描后再做页面隐藏，也避免下载时间段外的附件。

当前场景沿用已有约束：单租户、内部管理员、低并发手动任务；同一群聊同一时刻仍只允许一个采集任务。时间范围不会改变凭证保存和并发锁规则。

## 2. 时间语义

- 页面使用两个 `datetime-local` 输入，均必填，步长为 60 秒。
- 输入固定按北京时间（UTC+8）解释，不依赖浏览器或服务器所在时区。
- 开始分钟和结束分钟都包含。例如选择 `2026-08-21 10:00` 至 `2026-08-21 12:00`，业务区间为 `[10:00:00, 12:01:00)`。
- 开始分钟可以等于结束分钟，此时抓取这一分钟；开始分钟晚于结束分钟时拒绝创建任务。
- API 将用户输入转换为规范 UTC 时间，任务保存 `startTime`（包含）与 `endTimeExclusive`（排除）。失败任务恢复时复用这两个值，不允许重新指定范围。
- 新任务不支持省略时间范围。没有时间范围的旧任务仍可查看，但不能恢复，防止意外继续全量抓取。

## 3. 调用链路

1. Web 提交群聊 ID、开始分钟和结束分钟。
2. API 严格校验 `YYYY-MM-DDTHH:mm`，按 UTC+8 转为 UTC，并创建带范围的任务。
3. Job Runner 将规范范围传给 Python bridge；断点恢复复用任务中的范围与页令牌。
4. Python 调用飞书“获取会话历史消息”接口时传递 Unix 秒级 `start_time` 与 `end_time`。
5. Python 在下载附件和规范化消息之前，再按原始 `create_time` 执行 `[start, endExclusive)` 防御性过滤；这样无论飞书结束边界采用包含还是排除语义，都不会写入下一分钟的数据。
6. 页面任务区展示实际抓取的北京时间范围，并在零命中时给出“该时间段没有消息”的完成态。

飞书官方“获取会话历史消息”接口支持 `start_time`、`end_time` 查询参数；实现继续使用 `ByCreateTimeAsc`，保证任务内消息按发送时间正序进入时间线。

## 4. 兼容性与失败处理

- 任务 JSON 持久化时间范围，API 重启后仍可恢复相同范围。
- 页令牌只在同一范围内使用；恢复任务不能改变范围。
- 前端校验用于即时反馈，API 校验是最终安全边界。
- 飞书返回非法或缺失 `create_time` 的消息不会进入限定范围，也不会下载其附件。
- 区间内没有消息时任务正常完成，消息数为 0，不视为错误。

## 5. 验收标准

1. 页面只有在已选择群聊、开始时间和结束时间均有效时才能点击“开始采集历史记录”。
2. 页面明确说明时间按北京时间和飞书消息发送时间计算，输入精确到分钟。
3. 选择同一分钟时任务可创建；开始晚于结束时前端提示，绕过前端直接请求 API 也返回 400。
4. API 创建的任务持久化包含 UTC 规范的 `startTime` 与排他 `endTimeExclusive`，响应中不包含 Secret。
5. Python 请求飞书时传递正确的 `start_time` 与 `end_time` Unix 秒；分页请求始终复用同一范围。
6. 位于开始边界的消息被采集，位于结束分钟 `:59.999` 的消息被采集，位于下一分钟 `:00.000` 的消息被排除。
7. 时间段外消息的附件不会被下载；空结果正常完成且消息数为 0。
8. 失败任务恢复沿用原时间范围；没有范围的旧任务不能恢复。
9. 跨天范围按北京时间正确转换和抓取。
10. `corepack.cmd pnpm test`、`corepack.cmd pnpm typecheck`、`corepack.cmd pnpm build` 与 Python 单元测试全部通过。
11. 启动 Web/API 与本地假飞书服务，模拟“验证凭证 → 选择群聊 → 选择时间范围 → 开始采集 → 查看任务范围与消息”的完整用户流程，并单独列出失败步骤。
