# 飞书历史采集增量消息与附件复用设计

## 1. 使用场景

当前系统是单机、单租户、内部管理员手动发起的低并发历史采集工具。管理员选择一个飞书会话和北京时间范围后，可能反复采集相同或重叠区间。PostgreSQL 是消息与附件状态的权威元数据源，私有 OSS 是已上传附件的权威对象存储，本地任务目录是下载和失败恢复暂存层。

本轮目标是在不牺牲失败恢复能力的前提下，减少重叠范围采集产生的重复飞书附件下载、OSS 覆盖上传和无变化消息更新。

## 2. 目标与非目标

### 2.1 目标

1. 附件以 `message_id + file_key` 作为唯一身份，不按文件名去重。
2. 采集开始前批量读取所选会话和时间范围内的历史附件状态。
3. 历史附件为 `uploaded` 且 Bucket/Object Key 完整时，机器人和个人 CLI 都跳过飞书下载与 OSS 上传。
4. 历史附件为 `upload_failed`，且旧任务本地暂存文件仍有效时，复制到新任务暂存目录后直接重传 OSS，不重新访问飞书附件接口。
5. 无记录、`source_failed`、本地暂存无效或历史状态不完整时，正常下载并上传。
6. `pending` 附件不重复进入同一任务的后台队列。
7. 完全一致的消息和附件不刷新业务行的 `last_job_id`、`last_collected_at` 或 `updated_at`。
8. 保持分页令牌只在一页持久化成功后推进，失败任务可以按原范围恢复。

### 2.2 非目标

- 不在每次历史采集时对所有已上传 OSS 对象执行 HEAD；对象丢失检测应由独立审计任务处理。
- 不通过重新下载附件计算源文件哈希来证明字节一致；本轮把相同 `message_id + file_key` 视为同一个不可变飞书附件引用。
- 不扩展到多实例高并发调度。多实例部署前需要增加 PostgreSQL 级会话任务锁和附件租约。
- 不删除旧任务暂存文件，不改变现有私有 OSS Object Key。

## 3. 下载前决策

采集器先获取消息页元数据和附件 Key，再按以下状态处理：

| 历史状态 | 本地暂存 | 动作 |
| --- | --- | --- |
| 无记录 | 不适用 | 下载飞书附件并上传 OSS |
| `uploaded`，Bucket/Object Key 完整 | 不检查 | 复用历史元数据，跳过下载和上传 |
| `upload_failed` | 文件存在、普通文件、大小有效 | 复制到当前任务目录并直接上传 OSS |
| `upload_failed` | 文件缺失或无效 | 重新下载并上传 |
| `source_failed` / `not_configured` | 任意 | 重新下载并上传 |
| `pending` | 任意 | 当前任务不重复排队；新任务没有可靠完成结果时重新处理 |

为避免 N+1 查询，历史状态按会话和采集时间范围一次性批量读取，并在任务进程内建立 `message_id + file_key` 索引。

## 4. 两条采集链路

### 4.1 机器人

机器人 Python Bridge 在任务开始时收到可跳过下载的附件身份集合。消息规范化阶段：

- 命中集合：只返回 `pending` 附件占位，不调用飞书资源下载接口；API 持久化层把占位替换为历史 `uploaded` 元数据，或已复制的本地复用文件并上传。
- 未命中：保持现有下载逻辑。

### 4.2 个人 CLI

CLI 消息分页本来就不下载资源。API 保存页面前把 `pending` 占位与历史索引合并：

- `uploaded` 直接变为历史成功结果。
- 有效本地失败文件变为 `reused`，随后只执行 OSS 重传。
- 其余保持 `pending`，页面写入成功后才进入附件 Worker。

Worker 必须读取持久化后的页面，而不是原始飞书页面，避免已复用附件仍被重复排队。

## 5. 数据一致性与事务

消息和附件仍使用 PostgreSQL `INSERT ... ON CONFLICT`，但 `DO UPDATE` 增加业务字段 `IS DISTINCT FROM` 条件。只有来源字段、正文、附件状态或存储结果实际变化时才更新；任务进度和采集审计记录仍正常写入。

附件上传发生在数据库页事务之前。若 OSS 成功而数据库失败，确定性 Object Key 保证不会产生多个对象；后续可通过持久化上传结果进一步减少这种极端情况下的覆盖上传，本轮不改变该事务边界。

## 6. 本地复用安全条件

旧任务本地附件只有满足以下条件才允许复用：

1. `last_job_id`、`source_relative_path` 非空。
2. 解析路径位于对应旧任务目录内。
3. 文件存在且是普通文件。
4. 文件大小大于 0。
5. 历史 `size_bytes > 0` 时与实际大小一致。
6. 复制到当前任务目录成功。

条件不满足时不报任务级错误，回退为重新从飞书下载。

## 7. 验收标准

1. 同一范围首次采集无历史记录时，附件正常下载、上传并写为 `uploaded`。
2. 第二次采集相同消息和附件时，机器人附件下载调用为 0，OSS `uploadFile` 调用为 0。
3. 第二次 CLI 采集时，已上传附件不进入附件 Worker。
4. `upload_failed` 且旧本地文件有效时，飞书下载调用为 0，OSS 上传调用为 1。
5. `upload_failed` 但旧本地文件缺失或大小不一致时，重新下载并上传。
6. `source_failed` 或无记录时，重新下载并上传。
7. 同名但 `file_key` 不同的附件不会错误复用。
8. 完全一致的消息重复保存后，消息 `last_collected_at` 不变化；完全一致的附件 `updated_at` 不变化。
9. 分页失败时不推进本地分页进度；恢复任务仍使用原采集范围和身份。
10. API、Internal Collector 自动测试和全仓类型检查通过。
11. 启动 Web/API 后模拟“选择采集方式 → 选择会话与时间范围 → 开始采集 → 查看附件状态”的用户流程，并列出无法在假服务中覆盖的真实凭证步骤。
