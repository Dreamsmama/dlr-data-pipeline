# 飞书消息 @ 用户名解析设计

## 1. 问题与实际场景

飞书历史消息正文中的 `@_user_1`、`@_user_2` 是单条消息内部的占位符，不是稳定的用户 ID。飞书同时在消息级 `mentions` 数组中返回占位符、被提及用户 ID 和显示名称。当前采集器只把 `body.content` 展平成正文，未使用 `mentions`，因此采集页和内部数据页都会原样展示占位符。

当前系统是单租户、内部管理员按群采集并浏览历史数据。采集结果会先写本地任务页，再幂等写入 PostgreSQL；两个页面共用已经归一化的 `text` 字段。本轮应在采集归一化阶段完成解析，使采集页、内部数据页和后续使用方得到同一份正确正文，而不是只在某一个前端页面临时修饰。

## 2. 数据与安全边界

- 首选当前消息 `mentions[].name`，因为它与该条消息的占位符直接对应。
- 若 mention 有用户 ID 但姓名为空，才使用本次采集已取得的群成员 `ID → 姓名` 映射补充。
- `_user_1` 的编号只在当前消息中有意义，绝不按群成员顺序猜测。
- 映射缺失、格式异常或姓名为空时保留原占位符，避免把消息错误归属给其他人。
- 只替换完整的 `@占位符`；按占位符长度从长到短处理，避免 `_user_1` 误命中 `_user_10`。
- 删除消息仍展示统一删除提示；附件名称去重规则保持不变。

## 3. 实现方案

在 Python bridge 中增加纯函数 `resolve_mentions(text, mentions, members)`：

1. 读取每个 mention 的 `key`、`name` 和 `id`。
2. 将 key 规范为以 `@` 开头的正文标记，将姓名规范为只带一个 `@` 的展示文本。
3. 首选 mention 自带姓名，其次按 mention ID 查询群成员姓名。
4. 对正文进行字面量替换，不改动没有对应映射的文本。
5. `message_text` 在正文展平后、附件正文去重前调用该函数。
6. `normalize_message` 把当前群成员映射传给 `message_text`。

解析后的正文继续写入现有 `text` 字段，不增加数据库列，也不要求前端改动。这样能保持采集页与内部数据页展示一致，并避免查询阶段重复解析。

## 4. 历史数据处理

已经入库的旧记录只保留了解析后的 `text`，没有保留飞书原始 `mentions`。因此无法仅凭现有数据库可靠还原每个占位符对应的人名。

修复上线后，重新采集受影响群组和日期范围即可安全修复历史正文：飞书返回完整消息和 `mentions`，数据库以 `message_id` 幂等 upsert，并用新正文覆盖旧正文，不会重复增加消息。若飞书已不再返回该历史消息或应用权限不包含对应范围，则该记录只能保留占位符；不能用猜测替换。

## 5. 验收标准

1. 普通文本中的单个 `@_user_1` 按当前消息 mention 名称显示为 `@用户名`。
2. 同一消息包含多个 mention 时逐一正确替换；`@_user_1` 与 `@_user_10` 不串位。
3. 富文本展平后仍能正确替换多个 mention。
4. mention 姓名为空但 ID 能匹配群成员时，使用群成员姓名。
5. mention 姓名和群成员映射都缺失时保留原占位符，不报错、不误配。
6. 普通正文中没有 mention 映射的相似字符串不被改动。
7. 删除消息提示和附件名称去重行为保持不变。
8. 新采集任务写入的本地页与 PostgreSQL 正文均为解析后的用户名；同一消息重新采集后更新旧正文且不产生重复消息。
9. Python 单元测试、项目测试、类型检查和构建通过。
10. 服务以非沙盒方式重启后，按“飞书历史采集 → 选择含 @ 的消息时段 → 完成采集 → 内部数据 → 打开同一群组”的用户流程验证；记录无法自动完成的步骤和原因。

## 6. 本轮不做

- 不在前端根据群成员列表猜测或二次替换占位符。
- 不修改飞书历史消息本身。
- 不存储用户凭证，也不在没有用户重新授权的情况下主动重拉飞书数据。

## 7. 确定性 mention 回填方案

### 7.1 证据来源

旧群聊记录已经丢失 `mentions` 元数据时，使用官方 Lark CLI 的
`im +messages-mget`，按数据库现有的 `message_id` 批量读取同一条飞书消息。响应中的
`mentions[].key`、`mentions[].id`、`mentions[].name` 是消息级直接证据。

A/B/C 单聊中的相同时间、相同正文只能用于人工旁证，不能证明群消息实际 @ 的对象，
因此不得作为自动替换依据，也不得生成 `_user_1 -> 某人` 的群级全局映射。

### 7.2 可应用条件

一条群聊消息必须同时满足以下条件才允许替换：

1. `mget` 返回的 `message_id` 与数据库消息完全相同。
2. 返回的 `chat_id` 与目标群完全相同。
3. 数据库正文中的每个 `@_user_N` 都能在该消息自己的 `mentions` 中找到唯一且非空的名称。
4. 只按 `mentions[].key` 替换后，完整正文必须与 `mget` 返回的 `content` 完全相同。
5. 同一 key 出现冲突名称、消息被删除、缺少名称、正文还有未解析占位符或全文不一致时跳过。

多 mention 消息可以处理，但每个占位符都必须分别满足上述直接证据条件。

### 7.3 覆盖与回滚

- 新增 `feishu_mention_replacements` 审计表，保存消息 ID、原文、替换后正文和完整
  `key -> {id, name}` 映射。
- 默认只生成 dry-run 报告；只有显式 `--apply` 才写数据库。
- 应用时使用单个 PostgreSQL 事务：先写审计记录，再使用“消息 ID、群 ID、原文仍一致”
  的条件更新 `feishu_messages.text`；并发变化会令事务失败而不是覆盖新数据。
- 已替换或已有审计记录的消息不重复处理。可依据审计表的 `original_text` 精确回滚，
  不修改附件、发送者、时间或任务统计。

### 7.4 验收标准

1. 已验证样例消息 `om_x100b4c34b35bec800f437bab8acc2ba` 返回
   `_user_1 -> 李月`，解析后全文与飞书内容一致。
2. dry-run 输出目标群占位符消息数、确定候选数及各类跳过数量。
3. 单 mention 和多 mention 都按当前消息自己的元数据正确替换。
4. 错误群 ID、缺失/冲突名称、未完全解析和正文不一致时不生成候选。
5. apply 后更新条数与新增审计条数一致；任一并发条件失败时事务整体回滚。
6. 抽样核对内部数据页面，用户名展示正确，其他正文、附件和排序不变。
7. 单元测试、项目测试、类型检查和生产构建通过；服务重启后完成页面流程验证。
