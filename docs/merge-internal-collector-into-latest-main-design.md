# 将 internal collector 合入最新 main 的设计

## 目标场景

在同一个 DLR 管理后台中同时提供电商数据采集/导入能力和飞书内部数据采集/浏览能力，二者共享一个 Web 服务、一个 Fastify API 服务、数据库包和 OSS 存储包。

## 基线与范围

- 目标基线：最新 `origin/main`，保留其电商采集、商品管理、文件管理和部署修复。
- 合入来源：`feature/internal-collector`，保留飞书机器人/CLI 采集、内部消息浏览、附件处理和 PostgreSQL/OSS 持久化。
- 只解决两条业务线的集成问题，不改写现有采集业务规则。
- 不提交、不推送，等待人工页面验收后再决定。

## 集成设计

1. API 只启动一个 Fastify 实例，分别注册电商和飞书路由。
2. 首页和导航同时暴露电商、文件、导入、内部数据和飞书采集入口。
3. 数据库包保留电商查询/导入与飞书 Repository，并统一迁移记录格式。
4. OSS 包同时支持电商 SHA-256 幂等上传和飞书附件下载/预览能力。
5. 先解决各级 `package.json`，最后重新生成 `pnpm-lock.yaml`。
6. Web 全局样式保留两类页面，并检查公共选择器污染。

## 验收标准

- `/` 同时显示电商与内部数据入口。
- `/ecommerce`、`/imports`、`/internal-data`、`/collectors/feishu` 均可打开。
- `/health` 返回 200，且按用户要求使用 `postgres-oss`。
- 电商汇总/商品接口与飞书群聊查询接口均返回成功响应。
- API/采集器测试全部通过。
- 全工作区 TypeScript 类型检查通过。
- 生产构建通过。
- 在沙盒外启动 Web/API，并模拟上述页面访问流程。

## 风险与回退

- 数据库迁移兼容是最高风险，验证阶段不自动执行远端结构迁移。
- 若最新 main 带来新冲突，优先保留 main 的电商/部署修复，再按模块接入飞书功能。
- 合并未提交前可使用 `git merge --abort` 回到最新 main；不会删除用户生成数据或运行输出。
